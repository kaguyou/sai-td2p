## 3. Robustness & Crash Findings (WB Code & SDK Warm-Init Paths)

### CRITICAL / HIGH

1. **[HIGH] Dynamic FDB `m_fdb_info_set` lost across every Warm Boot -> broken MAC aging, neighbor punt, and MAC moves**
   - **Where:** `sonic-sairedis/vslib/SwitchStateBase.cpp:51-57, 3303-3318`; `sai-td2p-merge/sairedis/vslib/SwitchBCM56860HW.cpp:1710, 1755-1763`.
   - **Mechanism:** `dump_switch_database_for_warm_restart()` and the warm-boot constructor only save/load `m_fdb_info_set` when `m_switchConfig->m_useTapDevice` is true. `Sai.cpp:159-168` sets `useTapDevice = false` for `SwitchBCM56860HW`. After warm boot, `m_fdb_info_set` is empty. When any pre-WB dynamic MAC ages out in HW, `onFdbAged()` looks it up in `m_fdb_info_set`, misses, and returns early — `hwPuntNeighborsOnAge()` is skipped, `m_objectHash` keeps the stale `FDB_ENTRY`, orchagent never receives `SAI_FDB_EVENT_AGED`, and if the MAC later re-learns (even on a different port), `onFdbLearned()` sees the entry already in `m_objectHash` (`line 1710`) and drops the learn event.

2. **[HIGH] SDK `_soc_trident2_misc_init` runs during Warm Boot and clobbers live HW registers/memories (breaks ECMP RTAG7 hashing, QoS DSCP/dot1p remarking, ASF, and rewrites TDM live)**
