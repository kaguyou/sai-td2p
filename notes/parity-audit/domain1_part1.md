# Domain 1 SAI Parity Audit — `SwitchBCM56860HW` (TD2+ BCM56864 / Edgecore AS5812-54T) vs SONiC 202505 & Vendor Broadcom SAI

Status legend:
- **(a) HW**: Programmed to or read from ASIC hardware via OpenBCM SDK.
- **(b) silent no-op**: Accepted (`SAI_STATUS_SUCCESS`) in vslib `m_objectHash` only (or hardcoded fake value), zero ASIC effect / wrong HW state.
- **(c) error**: Returns SAI error (typically `SAI_STATUS_NOT_IMPLEMENTED` / `SAI_STATUS_NOT_SUPPORTED` / `SAI_STATUS_FAILURE`).
- **(d) never reached**: Caller path is unreachable on AS5812-54T (Gearbox PHY, VOQ/fabric chassis, DPU/DASH, etc.).

## 3. Robustness Bugs in `SwitchBCM56860HW.cpp`, `hwbcm_core.c`, `hwbcm_l2.c` (and Base vslib Affecting Domain 1)

### Critical / High Severity

1. **[HIGH] Unsynchronized concurrent access to `g_sgmii_applied[]`, `g_sgmii_applied_at[]`, `g_desired_speed[]`, and port SerDes APIs between SDK linkscan thread and SAI API thread**
   - **Location**: `hwbcm_core.c:237-244`, `470-520` (`hwbcm_linkscan_handler`, runs on SDK linkscan thread) vs `hwbcm_core.c:2750-2828` (`hwbcm_port_speed_set`, runs on SAI API thread).
   - **Details**: Zero locking or atomics protect `g_sgmii_applied[port]`, `g_sgmii_applied_at[port]`, or `g_desired_speed[port]`. Even worse, `hwbcm_linkscan_handler:492` calls `bcm_port_interface_set(unit, port, BCM_PORT_IF_SGMII)` concurrently with `hwbcm_port_speed_set:2797-2821` calling `bcm_port_autoneg_set` / `bcm_port_speed_set` / `bcm_port_interface_set`, which can leave the PHY/SerDes in an inconsistent state or trigger a flap loop.

2. **[HIGH] `SwitchBCM56860HW::set()` updates virtual DB *before* HW programming and never rolls back on HW failure (DB/HW desync)**
   - **Location**: `SwitchBCM56860HW.cpp:3135` vs `3191-3200`.
   - **Details**: `SwitchBCM56850::set(...)` commits the new attribute to `m_objectHash` at line 3135 before invoking `hwSetPort`/`hwSetSwitch`/`hwSetHash`/etc. If the HW call fails, it logs `(virtual state already updated)` and returns the error without restoring the previous attribute value. Subsequent `get()` calls return the failed value, and warm-boot save persists the bogus state.

3. **[HIGH] MAC Move events silently dropped — stale FDB & broken SVI L3 neighbors**
   - **Location**: `hwbcm_l2.c:395` (`BCM_L2_CALLBACK_MOVE_EVENT` → `add=1`) + `SwitchBCM56860HW.cpp:1708-1714` (`if (fdbHash.find(sid) != fdbHash.end()) return;`).
   - **Details**: When an active MAC moves from port A to port B in the same VLAN, the ASIC moves it and raises `MOVE_EVENT`/`LEARN_EVENT`. `process_packet_for_fdb_event` sees `(mac, vlan)` already in `fdbHash`, drops the event, never emits `SAI_FDB_EVENT_MOVE`, never updates `m_objectHash`/`m_fdb_info_set`, and skips `hwRefreshNeighborsOnLearn:1739` (so SVI L3 egress keeps pointing to port A!).

4. **[HIGH] `shell_sock_serve()` redirects process-wide `fd 1` (stdout) and `fd 2` (stderr) via `dup2()` and runs SDK commands without SAI API mutex**
   - **Location**: `hwbcm_core.c:715-738` (`shell_sock_serve`) and `819-837` (`shell_sock_stop`).
   - **Details**: While any `bsh` command executes on the debug socket, `dup2(client, 1)` / `dup2(client, 2)` steals stdout/stderr from every thread in `syncd` (sending unrelated `hwbcm_log` stderr writes to the socket client, and risking `SIGPIPE` if the client disconnects mid-command!). Furthermore, `shell_sock_stop` closes `g_shell_sock_fd` while the detached `shell_sock_main` thread may still be calling `accept(g_shell_sock_fd, ...)` (fd-reuse race on shutdown/re-init).

5. **[HIGH] All `BCM_E_*` errors collapsed to `SAI_STATUS_FAILURE` — no `SAI_STATUS_TABLE_FULL` / `INSUFFICIENT_RESOURCES` / `INVALID_PARAMETER` mapping**
   - **Location**: `SwitchBCM56860HW.cpp:42-45, 1013, 1159, 1377, 2006, 2035, 2210, 2245, 2339, 2418, 2525, 2558, 2603, 2626, 2655, 2699`.
   - **Details**: Only `HWBCM_E_NOT_FOUND` (-7) and `HWBCM_E_EXISTS` (-8) are recognized (and silently swallowed as success!). `BCM_E_FULL`, `BCM_E_RESOURCE`, `BCM_E_MEMORY`, `BCM_E_PARAM`, `BCM_E_UNAVAIL` all return generic `SAI_STATUS_FAILURE`. In SONiC `orchagent` (`saihelper.cpp`), `SAI_STATUS_TABLE_FULL` / `INSUFFICIENT_RESOURCES` are handled gracefully (retry/backoff), whereas `SAI_STATUS_FAILURE` triggers `handleSaiFailure(..., abort_on_failure=true)` and **aborts `orchagent`**!

6. **[HIGH] `hwRemoveLagMember()` mutates `m_lagMemberInfo` and `m_lagMembers` *before* `applyTrunkMembers(lag)`**
   - **Location**: `SwitchBCM56860HW.cpp:2873-2885`.
   - **Details**: If `applyTrunkMembers(lag)` fails at line 2884, `hwRemoveLagMember` returns error and `SwitchBCM56860HW::remove:3121` skips `SwitchBCM56850::remove` — leaving `SAI_OBJECT_TYPE_LAG_MEMBER` alive in `m_objectHash` AND the port still in the HW trunk, while `m_lagMemberInfo` has already been erased! Any retry of `remove_lag_member` hits `if (it == m_lagMemberInfo.end()) return SAI_STATUS_SUCCESS;` (line 2865), permanently leaking the HW trunk member and skipping `syncLagMemberPort(..., false)`.

7. **[HIGH] Data race on `g_link_cb`/`g_link_cookie` and `g_l2_cb`/`g_l2_cookie` + unsynchronized `g_knet[]` & `setvbuf(stderr)`**
   - **Location**:
     - `hwbcm_core.c:256-257, 524-535, 2414-2415, 2550-2551` (`g_link_cb`/`g_link_cookie` plain non-atomic globals read on linkscan thread, written on API thread).
     - `hwbcm_l2.c:377-378, 383, 411, 418-419, 441-442` (`hwbcm_l2_addr_handler` reads `g_l2_cb` at line 383 and `g_l2_cookie` separately at line 411 without lock/atomics).
     - `hwbcm_core.c:276, 2933-2946, 3264-3557` (`g_knet[]` mutated in `hwbcm_port_pvid_set`, `hwbcm_knet_netif_create/destroy/warm_recover` without `g_lock`, while `hwbcm_deinit` locks `g_lock`).
     - `hwbcm_core.c:122-125`: unsynchronized `if (!g_stderr_unbuffered) { setvbuf(stderr, ...); g_stderr_unbuffered = 1; }` callable concurrently from API/linkscan/L2/shell threads (UB per C standard if `stderr` already written or racing).

### Medium Severity

8. **[MEDIUM] Resource leak in `hwbcm_knet_netif_create()` on filter (b) failure (RIOT VFI filter leaked)**
   - **Location**: `hwbcm_core.c:3340-3361`.
